# Guild ↔ Kumiai contract

Version: **1.0.0**. This is the single spec both sides implement:

- **Kumiai** (this repo) serves it as an authenticated remote MCP server and as a REST/RPC API.
- **The guild plugin** (`hirokata-claude-marketplace/plugins/guild`) calls it when a project's
  `.guild/config.yaml` says `backend: kumiai`. With `backend: local` (the default) the guild keeps
  using `tursodb` and its own `schema.sql`, unchanged.

Kumiai stores the **whole guild warehouse** (full parity with guild `schema.sql` v9.3): every table,
every `v_*` view, and the event feed. Kumiai's Postgres is the source of truth in kumiai mode, so the
Kumiai UI sees the same goals, projects, requirements, plans and tasks the guild works on.

---

## 1. Transport and auth

| | |
|---|---|
| MCP endpoint | `POST <BETTER_AUTH_URL>/mcp` (Streamable HTTP, stateless) |
| Auth | OAuth 2.1 via Better Auth `@better-auth/mcp` (+ `jwt()`, `@better-auth/cimd`). Bearer access token. |
| Discovery | `/.well-known/oauth-protected-resource[/mcp]`, `/.well-known/oauth-authorization-server[/api/auth]` (issuer is `<origin>/api/auth`) |
| Login | the normal Kumiai `/login` page (only `hirokata.dev` accounts can exist), then `/consent` |
| REST/RPC | `POST /api/kumiai/guild/<tool_name>` — JSON body = the tool's input, JSON response = the tool's result. Session cookie **or** the same Bearer token. |

Add it to a project (project scope, fixed server name `kumiai` — the guild's agent files grant
`mcp__kumiai__*`):

```bash
claude mcp add --scope project --transport http kumiai https://<kumiai-host>/mcp
```

## 2. Rules every tool follows

1. **`workspace` is on every tool** (except `whoami` / `list_workspaces` / `create_workspace`). It is
   a Kumiai workspace id. The workspace must belong to the caller's team, else `FORBIDDEN`.
   The tools are stateless — no "current workspace" lives on the server.
2. **`actor` is on every write**: the guild member's name (`orchestrator`, `strategist`,
   `developer-svelte`, `user`, …). It replaces `UPDATE guild_state SET value=… WHERE key='actor'`.
   Kumiai records both `actor` and the authenticated user id on each event.
3. **Keys, not internal ids.** Every guild-shaped row has the guild's key: `GOAL-001`, `PROJ-001`,
   `REQ-001`, `PLAN-001`, `TASK-001`, `BUG-001`, `INSP-001`; graph nodes use the guild's
   `REQ-001/implement.auth-service` ids; docs use `slug`; coverage uses its text `id`. Keys are
   unique per workspace and **generated by the server** on create (next number, zero-padded to 3).
   Tools accept and return keys. (Kumiai keeps its own nanoid `id` internally; it also returns it.)
4. **Free text is plain JSON strings.** No hex encoding, no `;` hazards — the tursodb gotchas do
   not apply.
5. **One tool call = one transaction.** Composite tools (`create_task`, `instantiate_graph`,
   `resolve_gate`, `supersede_doc`, …) are atomic: all of it lands or none of it does.
6. **The guild deletes almost nothing.** The only delete tools are `unlink` (a knowledge edge),
   `remove_task_dependency`, and the direction deletes `delete_goal(s)` / `delete_project(s)`
   (§4.3). Work — requirements, plans, tasks, bugs — is retired by status.
7. **Every mutation writes an `event` row** (verb, subject_type, subject_id, payload), the same
   vocabulary as the guild's triggers, so `v_recent_activity` reads identically.
8. **Vocabularies are the guild's.** CHECK constraints from `schema.sql` are enforced in Postgres
   too. Violations return `VALIDATION`. So does an **argument the tool does not take**: unknown
   top-level input keys are refused, never silently dropped (a dropped `expect_status` would turn
   a guarded move into an unguarded one that still succeeds). The advertised input schemas say
   `additionalProperties: false`.
9. **Update semantics.** Every `update_*` / `upsert_*` is a patch: omitted fields keep their value,
   `null` clears a nullable field. Every status-moving tool (`update_goal/project/requirement/plan/bug/inspection`, `update_finding` on `disposition`, `set_task_status`, `set_node_status`) accepts `expect_status` as a guard
   (`CONFLICT` when it does not match), so a guarded move is one call, not a read-then-write.
10. **Errors** are MCP tool errors (`isError: true`) whose text is JSON:
   `{"code":"NOT_FOUND|FORBIDDEN|VALIDATION|CONFLICT|UNAUTHENTICATED|INTERNAL","message":"…"}`. REST returns
   the same body with 404/403/400/409/401/500. `INTERNAL` never carries internals.
11. **Timestamps** are ISO-8601 UTC strings (`2026-10-18T09:00:00Z`) on the wire.

## 3. Mapping onto Kumiai's existing tables

Kumiai already had goals, projects, requirements, plans, tasks. They gain the guild's columns; the
rest of the warehouse is new `kumiai_*` tables, all carrying `team_id` + `workspace_id`.

| Guild | Kumiai | Notes |
|---|---|---|
| `goal` | `kumiai_goals` + `key` | 1:1 |
| `project` | `kumiai_projects` + `key`, `concurrent`, `isolation`, `worktree_path` | Guild priority 1–5 ↔ Kumiai `urgent=1, high=2, medium=3, low=4` (5 is stored as `low`, read back as 4). Guild-created projects default `impact=50`, `effort=5`. Kumiai statuses `backlog` reads as `todo`; `blocked` is kept and is "not done". |
| `requirement` | `kumiai_requirements` + `key`, `workspace_id` | Unaffiliated requirements (`project` null) still belong to a workspace. |
| `plan` | `kumiai_plans` + `key`, `gate_node_id` | |
| `task` | `kumiai_tasks` + `key`, `files` (jsonb), `parallel_group`, `node_key`, `agent`, `claimed_by`, `claimed_at` | |
| `task_dependency`, `task_capability`, `graph_node`, `graph_edge`, `graph_deviation`, `gate`, `work_log`, `review_finding`, `bug`, `coverage`, `inspection`, `inspection_coverage`, `doc`, `knowledge_edge`, `doc_revision`, `event`, `guild_state` | `kumiai_<same name>` | New. Same columns + `workspace_id`. |
| every `v_*` view | Postgres view `kumiai_v_*` with a `workspace_id` column | Same name minus prefix, same columns, same rule. Read via `read_view`. |

## 4. Tools

Types: `Key` = guild key string; `Prio` = int 1–5; `?` = optional. Every result is an object: a single-row write returns the full row after the write (the equivalent of
`RETURNING *`), with keys, not internal ids — `id` is the guild key, `key` repeats it, `kumiai_id` is the
internal id. Composite tools return named parts (`resolve_gate` → `{gate, node, plan}` with `plan: null`
when no plan is linked, `instantiate_graph` → `{nodes, edges, gates, deviations}`, `supersede_doc` →
`{new, old, edge}`, `doc_neighbors` → `{type, id, rows}`, `claim_task` → `{task}`). A list of rows is
never bare: it is always under a name (`rows`, `workspaces`).

Rows carry the guild's column types: flags the guild stores as `0`/`1` (`project.concurrent`,
`task_capability.required`, …) are `0`/`1` integers, as in `schema.sql`. The one exception is the
`capabilities` array `get task` adds, whose `required` is a JSON boolean.

### 4.1 Context

| Tool | Input | Result |
|---|---|---|
| `whoami` | — | `{ user: {id,email,name}, team: {id,name}, contract: "1.0.0" }` |
| `list_workspaces` | — | `{ workspaces: [...] }` — the caller's team, default first. A workspace is `{id, name, isDefault, goalCount, projectCount, createdAt, updatedAt}` (Kumiai's own shape, camelCase). |
| `create_workspace` | `name` | the workspace (same shape). `CONFLICT` when the team already has that name. |
| `rename_workspace` | `workspace, name` | the workspace (same shape) with its new name. `CONFLICT` when another workspace of the team already has that name; renaming to its current name succeeds. The id, the default flag and the workspace's data never change. Writes no event (workspaces have none), so it takes no `actor`. |
| `get_state` | `workspace, key?` | `{ rows: [{key, value}] }` (all, or one) |
| `set_state` | `workspace, actor, key, value` | the row (upsert). Key `actor` writes nothing and returns `{key:'actor', value:<actor param>, ignored:true}` — attribution is per call. No event is written (the guild has no trigger on guild_state). |

### 4.2 Reads

`Where` = `{ col: scalar | scalar[] | {op, value?} }`. A scalar is equality, an array is `IN`, and
`op` ∈ `= <> < <= > >= like is_null not_null`. `like` takes a literal-with-wildcards pattern
(`%`, `_`, escape `\`), case-sensitive like SQLite's `GLOB`-free `LIKE` on ASCII. Timestamps compare
as instants. All conditions are ANDed.


| Tool | Input | Result |
|---|---|---|
| `read_view` | `workspace, view, where?: Where, order_by?: [{col, dir}], limit? (≤500, default 200), offset?` | `{ rows: [...], next_offset: int\|null }`. `view` is an enum of every guild view name (`v_brief`, `v_board`, `v_next_task`, `v_batch`, `v_ready_nodes`, `v_gates_pending`, … all of them). Unknown columns → `VALIDATION`. Page with `offset` until `next_offset` is null. |
| `get` | `workspace, type, key` | one row; `type` ∈ `goal, project, requirement, plan, task, bug, coverage, inspection, doc, review_finding, graph_node, gate`. Tasks include `capabilities` and `depends_on`. |
| `list` | `workspace, type, where?, order_by?, limit?, offset?` | rows of a base table, same filter and paging rules as `read_view`. Also accepts `work_log, task_dependency, task_capability, graph_edge, graph_deviation, knowledge_edge, doc_revision, event, inspection_coverage, gate, guild_state`. Foreign-key columns (`task_id`, `requirement_id`, …) hold and filter by guild keys. `graph_edge` and `gate` carry `requirement_id`. |
| `search_docs` | `workspace, query, kind?, limit?` | docs whose title/body contain `query` (case-insensitive, literal — no wildcards). |
| `check_invariants` | `workspace, process?, requirement?: Key` | `{ ok, failures: [{id, description, rows, advisory?}], checked: [id], skipped: [{id, reason}] }` — the global invariants of guild `docs/expectations.md`, and a named process's postconditions when `process` is given. `process` ∈ `new-requirement, brief, dashboard, check-in, release, qa, shift`. `new-requirement` is per requirement and **requires** `requirement` (`VALIDATION` without it). `rows` are the offending rows as arrays of strings (`[breach, row_id, detail]`, NULL as `""`). `ok` is false iff a non-advisory failure exists (§9.c is advisory: the pre-release gate warns). `skipped` names every assertion that stays local (roster, git, the dashboard file, before/after comparisons) with the reason. |
| `fingerprint` | `workspace` | `{ tables: {<table>: {count, max_key, digest}} , events: {count, max_id} }` — the before/after fingerprint release §9.a compares. `digest` is an md5 over the table's rows in key order, so a changed row shows even when count and max key do not. |

### 4.3 Direction — goals and projects

| Tool | Input |
|---|---|
| `create_goal` | `workspace, actor, title, body?, priority?: Prio, status?` |
| `update_goal` | `expect_status?, workspace, actor, key, title?, body?, priority?, status?` |
| `create_project` | `workspace, actor, goal: Key, title, body?, ordinal?: int\|null, priority?, status?, concurrent?: bool, isolation?: 'shared'\|'worktree', worktree_path?` |
| `update_project` | `expect_status?, workspace, actor, key, …any create field except goal` |
| `delete_goal` | `workspace, actor, key, cascade_projects?: bool, expect_status?` — permanent. `CONFLICT` while the goal has projects unless `cascade_projects` is true, which deletes them too. Returns `{ deleted: [key], projects_deleted: [key], requirements_detached: [key] }`. |
| `delete_goals` | `workspace, actor, keys: Key[] (1–100), cascade_projects?: bool` — `delete_goal` for many, in one transaction: all or none. `NOT_FOUND` names every missing key. Duplicate keys count once. |
| `delete_project` | `workspace, actor, key, expect_status?` — permanent. Requirements under it are **detached** (they become unaffiliated), never deleted. Returns `{ deleted: [key], requirements_detached: [key] }`. |
| `delete_projects` | `workspace, actor, keys: Key[] (1–100)` — `delete_project` for many, in one transaction: all or none. |

The four delete tools also remove the knowledge edges that name the deleted goal or project (so
`v_knowledge_dangling` stays empty) and each write a `deleted` event. They are the exception to
rule 6, and only for direction rows: requirements, plans, tasks and everything beneath them are
still retired by status, never deleted.

### 4.5 Execution graph and gates

| Tool | Input |
|---|---|
| `instantiate_graph` | `workspace, actor, requirement: Key, nodes: [{node_key, suffix?, kind: 'work'\|'gate', task?: Key, parallel_group?, status?, gate?: {prompt, kind?}}], edges: [{from: nodeRef, to: nodeRef}], deviations?: [{kind, node_key, reason}]` — atomic. The node id is `<REQ>/<node_key>` or `<REQ>/<node_key>.<suffix>` (a fanned node: `REQ-001/implement.TASK-011`); `node_key` is stored exactly as given (`implement`), never with the suffix. `nodeRef` is `node_key` or `node_key.suffix`. Returns nodes + edges. |
| `add_graph_node` | `workspace, actor, requirement, node_key, suffix?, kind, task?, parallel_group?, gate?` |
| `add_graph_edge` | `workspace, actor, from: nodeId, to: nodeId` |
| `add_graph_deviation` | `workspace, actor, requirement, kind, node_key, reason` |
| `set_node_status` | `workspace, actor, node: nodeId, status, expect_status?, task?: Key` (binds task when given; `expect_status` guards like `set_task_status`) |
| `resolve_gate` | `workspace, actor, node: nodeId, status: 'approved'\|'rejected', decision?, decided_by? (default 'user'), plan?: Key` — atomic "two writes": sets the gate; the plan is `plan` if given (its `gate_node_id` is set to `node`), else the plan whose `gate_node_id = node`; that plan gets `approval`, `approved_by = decided_by`, `approved_at`, and on reject `status = 'in-progress'` (back to drafting). The node becomes `done` on approve and `skipped` on reject — the guild's spelling. |

### 4.7 Library — docs and the knowledge graph

| Tool | Input |
|---|---|
| `upsert_doc` | `workspace, actor, slug, title, body, kind?, status?, area?, source?` — snapshots the previous version into `doc_revision`. A new doc defaults to `kind='reference'`, `status='current'`; on update, omitted fields keep their value. |
| `link` | `workspace, actor, rel, from: {type, id}, to: {type, id}, note?` — the referential check the guild does by hand: both ends must exist, else `NOT_FOUND`. Idempotent on the unique tuple. |
| `unlink` | `workspace, actor, rel, from, to` |
| `supersede_doc` | `workspace, actor, old_slug, new: {slug, title?, body?, kind?, area?, source?}, note?` — atomic: writes the new doc, adds `supersedes` new→old, sets old `status='superseded'`. `title` and `body` go together; omit both when `new.slug` already exists (the librarian wrote it and reported the supersession) and the new doc is left as written while the edge and the status move — the orchestrator's half. `NOT_FOUND` when they are omitted and the doc does not exist. |
| `doc_neighbors` | `workspace, type, id, rel?` — one hop, both directions (there is no traversal; loop and cap in the caller) |

### 4.9 Boards (Kumiai only, not used by the guild)

The board/card tools from the old stdio `apps/mcp` server are served from the same endpoint:
`get_board, create_column, rename_column, delete_column, reorder_columns, create_card, get_card,
update_card, move_card, reorder_cards, delete_card, list_labels, create_label, update_label,

`create_board_project`, update/delete likewise `*_board_project`, add/remove_card_assignee,

### 4.10 Import

| Tool | Input |
|---|---|
| `import_guild` | `workspace, actor, source, dry_run?: bool` — loads a local guild board into an **empty** workspace. `source` is the `.guild/guild.db` as JSON: `schema_version` (9) plus, per table (`goal, project, requirement, plan, task, task_dependency, task_capability, graph_node, graph_edge, graph_deviation, gate, work_log, review_finding, bug, coverage, inspection, inspection_coverage, doc, doc_revision, knowledge_edge, event, guild_state`), the rows as `SELECT *` returns them; a table left out is empty. Atomic. Keys are kept; integer ids (findings, log lines, events) are renumbered and every reference to them follows; the event feed is the file's own. `CONFLICT` when the workspace already holds guild data; `VALIDATION` for a wrong `schema_version`, an unknown table, a row pointing at a key not in the file, or a value Postgres refuses. `dry_run` does everything and rolls it back. Returns `{ workspace, dry_run, counts: {<table>: n}, warnings: [..] }`. |

The server cannot read a file on the caller's machine, so the caller sends the rows. `pnpm guild:import
<project> --export board.json` writes `source` for you; `pnpm guild:import <project> --workspace …` imports
the file directly into `DATABASE_URL` with the same code.

## 5. Guild-side configuration

```yaml
# .guild/config.yaml
backend: kumiai        # local (default) | kumiai
kumiai:
  url: https://<kumiai-host>
  workspace: <workspace id>
```

`mode: local|cloud` (tursodb vs turso cloud) only applies to `backend: local`.

Bump this file's version on any breaking change; `whoami` returns `contract: "1.0.0"` so the guild

## 7. Alignment notes (1.0.0)

Resolved while driving the guild's kumiai prose end to end against this server
(`apps/api/test/guild/lifecycle.test.ts`). Where this file was silent, the resolution is now
written above; this list says which side moved.

- **Unknown arguments are `VALIDATION`** (§2 rule 8). Server changed: it used to strip them.
- **Result shapes are named, never bare** (§4 intro). Guild prose changed: `get_state` returns
  `{rows}`, and a preflight `list` is empty when `rows` is `[]`.
- **`check_invariants` returns `checked`, `skipped` and `advisory`** next to `ok` and `failures`,
  and `new-requirement` requires `requirement` (§4.2). Guild prose changed to match.
- **`fingerprint` carries a per-table `digest`** (§4.2). Recorded; the guild compares whole entries.
- **§7 C.b is unscoped by design: only the orchestrator moves status.** Every `moved`,
  `node-moved`, `decided` or `claimed` event whose actor is not `orchestrator` or `user` is a
  breach, on every subject — `plan`, `bug`, `doc` and `inspection` included. Guild prose changed:
  the strategist, qa-tester and librarian used to move a plan, a bug and a doc themselves; each now
  reports the outcome and the skill that spawned it makes the move as `orchestrator`. Server
  changed: `supersede_doc` accepts `new` without `title`/`body` when that doc already exists, so
  the librarian writes the new page and the orchestrator makes the edge-plus-status move in one
  call (§4.7).
