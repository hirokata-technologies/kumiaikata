# Migrate apps/api from Mongoose to Native MongoDB Driver

## Summary

This requirement covers the complete replacement of Mongoose with the official `mongodb` npm package as the data-access layer in `apps/api`. The migration is a pure internal refactor: every HTTP route, request/response contract, HTTP status code, and observable API behaviour defined in REQ-002 remains identical. No changes are made to collection names, document field names, or the shape of data stored in MongoDB.

The motivation is to remove the Mongoose abstraction layer and work directly with the MongoDB Node.js driver. This eliminates Mongoose schema-level validation (superseded by the existing `@hono/zod-validator` route layer), removes implicit `__v` version keys and other Mongoose-specific document fields, and allows the codebase to use the driver's aggregation and session APIs without translation through Mongoose wrappers.

TypeScript types for all MongoDB documents are derived exclusively from Zod schemas via `z.infer<>`. The same Zod schemas already used by route validators define document shapes, so there is no duplication between validation types and database types. All seven Mongoose models are replaced by typed native collection accessors, and all service-layer queries are rewritten using the native driver's CRUD and aggregation APIs.

## User Stories

### US-1: Replace Mongoose Connection with Native MongoClient

**As a** developer running `apps/api`
**I want** the server to connect to MongoDB using `MongoClient` from the `mongodb` package
**So that** there is no Mongoose dependency in the connection bootstrap path

**Acceptance Criteria:**

1. Given `MONGODB_URI` is set in the environment
   When `src/index.ts` starts
   Then `connectDB()` is called and awaited before the Hono server begins accepting requests, and a successful connection is logged

2. Given `connectDB()` resolves successfully
   When any route handler executes
   Then it accesses the database via `db.collection<DocType>("collectionName")` where `db` is the `Db` instance returned from `MongoClient.db()`

3. Given `MONGODB_URI` is missing or the MongoDB host is unreachable
   When `connectDB()` is called
   Then the process exits with a non-zero code and logs a descriptive error before any port is bound

4. Given `db/connection.ts` is imported
   Then it exports:
   - `client`: the `MongoClient` instance
   - `db`: the `Db` instance
   - `connectDB()`: async function that opens the connection
   - `withTransaction(cb)`: async helper that begins a client session, calls `session.withTransaction(cb)`, and closes the session on completion or error

**Edge Cases:**

- Calling `connectDB()` more than once: the function must be idempotent — if the client is already connected, it must not open a second connection.
- `withTransaction` callback throws: the session is aborted and the error is re-thrown to the caller; the session is always closed in a `finally` block.

### US-2: Replace Mongoose Models with Zod Document Schemas and Typed Collections

**As a** developer writing service-layer code
**I want** MongoDB document shapes defined as Zod schemas with inferred TypeScript types
**So that** there is a single source of truth for both validation and type-checking with no hand-written interfaces

**Acceptance Criteria:**

1. Given the directory `apps/api/src/db/schemas/` is created
   When a developer imports from it
   Then they find one file per collection, each exporting a Zod schema (e.g., `BoardSchema`) and an inferred type (e.g., `type Board = z.infer<typeof BoardSchema>`)

2. Given the following seven collections exist in the current Mongoose codebase — `boards`, `columns`, `cards`, `teams`, `teamMembers`, `labels`, `cardLabels` — (plus any Better Auth collections managed by that library)
   When the schemas directory is complete
   Then each of those seven collections has a corresponding Zod schema file; Better Auth collections are not included as they are managed by `better-auth`'s own MongoDB adapter

3. Given a Zod document schema for a collection
   Then it includes an `_id` field typed as `z.instanceof(ObjectId)` or equivalent, all required fields present in the current Mongoose schema, and all optional fields marked with `.optional()` or `.nullable()` as appropriate

4. Given a collection is accessed in a service
   Then the collection is typed as `Collection<DocType>` where `DocType` is the type inferred from the corresponding Zod schema (e.g., `db.collection<Board>("boards")`)

5. Given Mongoose schema-level validators (e.g., `required`, `enum`, `minlength`) previously defined in Mongoose models
   When the migration is complete
   Then those validators are removed from the data layer entirely and validation responsibility rests solely with the `@hono/zod-validator` middleware in the route layer

**Edge Cases:**

- `_id` handling: Native driver documents use `ObjectId` for `_id` by default; the Zod schema must reflect this, and any serialisation to JSON in route handlers must convert `ObjectId` to string.
- Mongoose virtual fields: Any Mongoose virtuals (e.g., `id` as a string alias for `_id`) are not replicated; callers must use `_id` directly and convert at the response-serialisation boundary.

### US-3: Replace Mongoose Query API with Native Driver CRUD Operations

**As a** developer reading service-layer code
**I want** all database reads and writes to use the `mongodb` driver's `Collection` API directly
**So that** there are no Mongoose model method calls (`Model.find`, `Model.save`, `doc.save()`, etc.) remaining in the codebase

**Acceptance Criteria:**

1. Given any service file under `apps/api/src/services/`
   When reviewed after migration
   Then it contains zero imports from `mongoose` and zero usage of Mongoose model methods (`find`, `findOne`, `findById`, `create`, `save`, `updateOne`, `deleteOne`, `findByIdAndUpdate`, etc.)

2. Given a service operation that previously used `Model.findById(id)`
   When rewritten
   Then it uses `collection.findOne({ _id: new ObjectId(id) })` with appropriate null-check and HTTP 404 handling if the document is not found

3. Given a service operation that previously used `Model.create(data)` or `new Model(data).save()`
   When rewritten
   Then it uses `collection.insertOne(data)` and returns `insertedId` for downstream use

4. Given a service operation that previously used `Model.findByIdAndUpdate(id, update, { new: true })`
   When rewritten
   Then it uses `collection.findOneAndUpdate({ _id: new ObjectId(id) }, update, { returnDocument: "after" })`

5. Given a service operation that previously used `Model.deleteOne({ _id: id })` or `doc.remove()`
   When rewritten
   Then it uses `collection.deleteOne({ _id: new ObjectId(id) })`

6. Given all existing route handler tests or integration checks
   When run after migration
   Then they pass without modification to the test assertions (observable behaviour is unchanged)

**Edge Cases:**

- `ObjectId` conversion: Any route parameter that is a MongoDB ID string must be wrapped with `new ObjectId(id)` before use in a query filter; if the string is not a valid 24-character hex ObjectId, the `ObjectId` constructor throws and the service must catch this and return HTTP 400 or HTTP 404 as appropriate.
- Projection: Where Mongoose `.select("-field")` was used, it is replaced with native projection syntax: `{ field: 0 }` in the `FindOptions`.

### US-4: Replace Mongoose Aggregation Pipeline with Native Driver Aggregation

**As a** developer maintaining `auth/middleware.ts`
**I want** the `fetchBoardWithMembership` aggregation to use the native driver's `collection.aggregate()` API
**So that** the aggregation runs without any Mongoose pipeline wrapper

**Acceptance Criteria:**

1. Given `auth/middleware.ts` currently uses a Mongoose model to run an aggregation pipeline
   When rewritten
   Then it calls `db.collection("boards").aggregate([...])` and calls `.toArray()` or iterates the cursor to retrieve results

2. Given the aggregation joins `boards` with `teamMembers` (or equivalent) to determine whether the requesting user has access to a given board
   When the native aggregation is complete
   Then it returns the same logical result as the Mongoose version: the board document plus the user's membership/role information

3. Given any other aggregation pipelines that existed in services (e.g., computing board statistics or fetching boards with nested columns/cards)
   When rewritten
   Then they produce identical output to the Mongoose versions, verified by the existing integration checks

4. Given the aggregation cursor is opened
   Then it is always closed after use, either by calling `.toArray()` (which closes automatically) or by calling `.close()` in a `finally` block if iterating manually

**Edge Cases:**

- `$lookup` stage: Native driver `$lookup` syntax is identical to Mongoose's; no translation is needed for the pipeline stages themselves. The only change is the calling convention (from `Model.aggregate()` to `collection.aggregate()`).
- Empty result: If the aggregation returns no documents, the middleware treats this as "board not found or not accessible" and returns HTTP 404 or HTTP 403 as appropriate.

### US-5: Replace Mongoose Session/Transaction API with Native `withTransaction` Helper

**As a** developer writing multi-document atomic operations
**I want** to use a `withTransaction(cb)` helper exported from `db/connection.ts`
**So that** transaction boilerplate (start session, commit, abort, close) is centralised and not repeated across services

**Acceptance Criteria:**

1. Given `db/connection.ts` exports `withTransaction(cb: (session: ClientSession) => Promise<T>): Promise<T>`
   When a service calls `withTransaction(async (session) => { ... })`
   Then the helper starts a `ClientSession` via `client.startSession()`, calls `session.withTransaction(cb)`, and ensures `session.endSession()` is called in a `finally` block

2. Given the personal board provisioning logic (triggered on first login per US-2 in REQ-002)
   When rewritten without Mongoose
   Then it uses `withTransaction` to atomically insert the user document and personal board document in the same transaction if it previously relied on a Mongoose session

3. Given the team and team board provisioning logic (triggered on domain's first login per US-3 and US-4 in REQ-002)
   When rewritten without Mongoose
   Then it uses `withTransaction` for the atomic find-or-create team + board operations if it previously relied on a Mongoose session

4. Given a callback passed to `withTransaction` throws an error
   When the helper handles it
   Then the transaction is aborted, the session is ended, and the original error is re-thrown to the caller

**Edge Cases:**

- MongoDB standalone instance (no replica set): `withTransaction` requires a replica set or sharded cluster. In local development environments without a replica set, the helper must fail with a clear error message indicating transactions are not supported on standalone instances. The Railway deployment must use a MongoDB Atlas or replica-set-enabled connection string.
- Nested transactions: MongoDB does not support nested transactions; callers must not call `withTransaction` inside another `withTransaction` callback.

### US-6: Remove `mongoose` Dependency and Update `package.json`

**As a** developer managing `apps/api` dependencies
**I want** `mongoose` removed from `apps/api/package.json` and `mongodb` added as a direct dependency
**So that** the dependency graph reflects actual usage and no unused packages are installed

**Acceptance Criteria:**

1. Given `apps/api/package.json` before migration
   When the migration is complete
   Then `mongoose` does not appear in `dependencies` or `devDependencies`

2. Given `apps/api/package.json` after migration
   Then `mongodb` appears as a direct entry in `dependencies` with an explicit version pinned (e.g., `"mongodb": "^6.x.x"`)

3. Given that `better-auth`'s MongoDB adapter already uses `mongodb` as a transitive dependency
   When `mongodb` is added as a direct dependency
   Then the version specified must be compatible with (or the same as) the version `better-auth` requires, to avoid duplicate installations

4. Given the migration is complete
   When `pnpm install` is run from the monorepo root
   Then it completes without error and no `mongoose`-related peer dependency warnings appear

5. Given all other packages in the monorepo (`apps/web`, shared packages)
   When `mongoose` is removed from `apps/api`
   Then none of them are affected — they do not import from `apps/api`'s internal modules

**Edge Cases:**

- `@types/mongoose`: If this devDependency exists in `apps/api/package.json`, it must also be removed as it is no longer needed.
- Lock file: The `pnpm-lock.yaml` at the monorepo root must be updated and committed along with `package.json`.

### US-7: Partial Unique Indexes Must Be Recreated as Native `createIndex` Calls

**As a** developer ensuring data integrity constraints
**I want** the partial unique indexes previously defined in Mongoose schemas to be recreated via a native `ensureIndexes()` startup function
**So that** the database enforces one personal board per user and one team board per team at the storage level

**Acceptance Criteria:**

1. Given a function `ensureIndexes()` defined in `db/connection.ts` or a dedicated `db/indexes.ts` file
   When called during application startup (after `connectDB()` resolves, before the server accepts requests)
   Then it calls `collection.createIndex(...)` with `{ unique: true }` and the appropriate partial filter expression for each constrained collection

2. Given the personal board constraint (one personal board per user)
   When `ensureIndexes()` runs
   Then it creates a unique index on `boards` with a partial filter expression matching documents where `type === "personal"`, keyed on the `ownerId` field (or equivalent field name used in the current schema)

3. Given the team board constraint (one team board per team)
   When `ensureIndexes()` runs
   Then it creates a unique index on `boards` with a partial filter expression matching documents where `type === "team"`, keyed on the `teamId` field (or equivalent field name used in the current schema)

4. Given the indexes already exist in MongoDB from a previous startup
   When `ensureIndexes()` is called again
   Then it completes without error (native `createIndex` is idempotent when the index definition has not changed)

5. Given any other indexes previously defined in Mongoose schemas (e.g., indexes on `teamMembers` for fast membership lookup)
   When `ensureIndexes()` runs
   Then those indexes are also recreated via `createIndex` calls

**Edge Cases:**

- Index definition conflict: If an existing index has the same name but a different definition (e.g., a leftover from a previous schema iteration), `createIndex` will throw. The `ensureIndexes()` function must not silently swallow this error; it must propagate so startup fails visibly.
- Field name verification: The partial filter expression field names and index key field names must exactly match the document field names used in the Zod schemas and collection writes; any mismatch means the index silently does not fire.

3. Given the build command for `apps/api` (e.g., `pnpm build` in `apps/api`)
   When executed after migration
   Then it exits with code 0 and produces a valid output artefact

4. Given no Mongoose types remain in the codebase
   When TypeScript checks all files under `apps/api/src/`
   Then there are zero references to `mongoose`, `Document`, `Model<T>`, `Schema`, or other Mongoose-specific types

- `ObjectId` import source: `ObjectId` must be imported from `mongodb`, not from `mongoose.Types.ObjectId`.

## Technical Considerations

- **Dependency change**: Remove `mongoose` from `apps/api/package.json`; add `mongodb` as a direct dependency. The version must align with what `better-auth`'s MongoDB adapter already uses as a transitive dependency to avoid duplicate installs.
- **Better Auth unchanged**: `better-auth`'s MongoDB adapter already uses the native driver internally. No changes are needed to the Better Auth configuration, session handling, or its collections.
- **Zod schemas location**: New directory `apps/api/src/db/schemas/`. One file per collection. Each file exports a Zod schema and a `z.infer<>` type alias.
- **Connection module exports**: `db/connection.ts` must export `client` (`MongoClient`), `db` (`Db`), `connectDB()`, and `withTransaction(cb)`.
- **Startup sequence in `src/index.ts`**: `await connectDB()` then `await ensureIndexes()` then bind the HTTP port. Any failure in either async step must abort startup.
- **ObjectId serialisation**: Route handlers that return documents must convert `_id: ObjectId` to `_id: string` (or `id: string`) before sending JSON responses. This was previously handled implicitly by Mongoose's `.toJSON()` transform; it must now be handled explicitly at the response-serialisation boundary.
- **Aggregation**: The `fetchBoardWithMembership` pipeline in `auth/middleware.ts` is the primary aggregation to rewrite. The pipeline stage syntax (`$lookup`, `$match`, `$project`, etc.) is driver-agnostic and does not change; only the calling convention changes.
- **No schema migration**: Collection names and document field names stay identical. No `db.renameCollection` or data transformation scripts are needed.
- **`fractional-indexing`, `hono`, `@hono/zod-validator`, `@hono/node-server`**: All remain unchanged.
- **Performance**: The native driver and Mongoose both use the same underlying MongoDB wire protocol. No performance regression is expected; however, removing Mongoose's document hydration (converting raw BSON to Mongoose `Document` instances) may slightly reduce per-query overhead.
- **Transactions require replica set**: Local development must use MongoDB Atlas (free tier) or a local replica set (e.g., via `mongod --replSet`). A standalone `mongod` does not support multi-document transactions.

## Out of Scope

- Any changes to HTTP routes, URL patterns, request body shapes, response body shapes, or HTTP status codes defined in REQ-002.
- Database schema changes: collection names and document field names remain identical to what Mongoose was using.
- Changes to `apps/web` or any other package in the monorepo.
- Adding new API features or modifying existing business logic.
- Migrating existing data: no data transformation scripts or MongoDB migrations.
- Changes to Better Auth configuration, its collections, or its adapter.
- Adding new indexes beyond those that already existed (implicitly or explicitly) in the Mongoose schemas.
- Integration or end-to-end test authoring: the requirement is that existing checks pass, not that new ones be written.
- Switching MongoDB hosting provider or changing the `MONGODB_URI` format.
