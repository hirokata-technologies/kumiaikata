# Kanban Board Management API

## Summary

This requirement defines a backend REST API for a kanban board application built with Hono on Node.js, backed by MongoDB, and deployed to Railway. The API serves as the sole data and business-logic layer for the kanban experience; no frontend implementation is included in this scope.

Authentication is handled by Better Auth with a Google SSO adapter. Access is gated by a domain allow-list: only email addresses belonging to approved domains may register or sign in. On first login each user receives an automatically provisioned personal board. Users are also automatically enrolled in a shared team board corresponding to their email domain; that team board is created when the first user from a given domain signs in.

Boards contain ordered columns, and columns contain ordered cards. Cards support a rich set of fields — title, description, labels, assignees, due date, comments, checklists, and file attachments. All connected clients receive live updates via Server-Sent Events (SSE) so that concurrent edits are visible without a page refresh. Team members carry one of two roles — Admin or Member — which governs who may modify column structure and team settings.

## User Stories

### US-1: Authentication and Registration via Google SSO

**As a** prospective user
**I want to** sign in using my Google account
**So that** I can access the kanban board without managing a separate password

**Acceptance Criteria:**

1. Given a user whose Google account email domain is on the server's `ALLOWED_DOMAINS` list
   When they complete the Google OAuth consent flow directed at `POST /api/auth/google`
   Then the API creates or retrieves their account, issues a session token, and returns HTTP 200 with the session payload

2. Given a user whose Google account email domain is NOT on the `ALLOWED_DOMAINS` list
   When they attempt to complete the OAuth flow
   Then the API returns HTTP 403 with a message indicating their domain is not permitted, and no account is created

3. Given an existing user with an active session
   When they call `POST /api/auth/signout`
   Then their session is invalidated and subsequent requests with that token return HTTP 401

4. Given a request to any protected endpoint without a valid session token
   When the request is processed
   Then the API returns HTTP 401

**Edge Cases:**

- Revoked Google token: If Google revokes the OAuth token mid-session, the next API request requiring Google token validation must return HTTP 401, forcing re-authentication.
- Domain allow-list change at runtime: If a domain is removed from `ALLOWED_DOMAINS` after users from that domain have already registered, existing sessions for those users remain valid until they expire; no retroactive account deletion is performed.
- Concurrent first-login race: If two requests for the same Google account arrive simultaneously (e.g., double-click), the API must be idempotent — exactly one account is created.

### US-2: Personal Board Auto-Provisioning

**As a** newly registered user
**I want to** have a personal board ready immediately after my first login
**So that** I can start organising my own tasks without any setup steps

**Acceptance Criteria:**

1. Given a user signing in for the first time
   When their account is successfully created
   Then the API automatically creates exactly one personal board assigned to that user, with no columns and no cards

2. Given a user who already has a personal board
   When they sign in again
   Then no additional personal board is created (idempotent provisioning)

3. Given an authenticated user
   When they call `GET /api/boards/personal`
   Then the API returns the user's personal board including its columns and cards

4. Given an authenticated user
   When they call `GET /api/boards/personal`
   Then the response includes the board's `id`, `title` (defaulting to "{First Name}'s Board"), `columns` array, and `createdAt` timestamp

**Edge Cases:**

- Board provisioning failure: If the database write for the personal board fails during account creation, the failure must be logged with sufficient context to allow a manual remediation; the user account itself is still created.
- User with no first name from Google profile: The default board title falls back to "My Board" when Google does not provide a given name.

---

### US-3: Team Auto-Join by Email Domain

**As a** user whose email belongs to an allowed domain
**I want to** be automatically added to my domain's team
**So that** I can collaborate on the shared team board without an invitation workflow

**Acceptance Criteria:**

1. Given a user signing in whose email domain maps to an existing team
   When their account is created
   Then they are automatically added to that team with the Member role

2. Given a user signing in whose email domain does not yet have a team
   When their account is created
   Then the API creates a new team for that domain and adds the user as its first Admin

3. Given an authenticated user who belongs to a team
   When they call `GET /api/teams/mine`
   Then the API returns their team including `id`, `domain`, `name` (defaulting to the domain string), and their own `role` within the team

4. Given a second user from the same domain signing in after the team already exists
   When their account is created
   Then they are added as a Member (not Admin) regardless of sign-in order after the initial Admin

**Edge Cases:**

- Multiple simultaneous first-logins from the same new domain: The API must use an atomic find-or-create operation (e.g., MongoDB `findOneAndUpdate` with `upsert`) so that exactly one team is created.
- Allowed domain removed after team creation: Existing team membership and the team board remain intact; only new sign-ins from that domain are blocked.

---

### US-4: Team Board Auto-Provisioning

**As a** team
**I want to** have a shared board created automatically when the team is initialised
**So that** the team can start collaborating immediately without manual setup

**Acceptance Criteria:**

1. Given a team being created for the first time (triggered by the first user from that domain)
   When the team is persisted
   Then the API automatically creates exactly one board associated with that team, with no columns and no cards

2. Given an authenticated user who belongs to a team
   When they call `GET /api/boards/team`
   Then the API returns the team board including its columns and cards

3. Given the team board response
   Then it includes `id`, `title` (defaulting to "{domain} Board"), `teamId`, `columns` array, and `createdAt` timestamp

**Edge Cases:**

- Team board provisioning failure: Same recovery posture as US-2 — log and allow manual remediation; the team record itself is still created.

### US-5: Column CRUD and Reordering

**As a** team Admin (for the team board) or the board owner (for a personal board)
**I want to** create, rename, delete, and reorder columns
**So that** I can structure the board to match the team's workflow

**Acceptance Criteria:**

1. Given an authenticated Admin (team board) or owner (personal board)
   When they call `POST /api/boards/:boardId/columns` with `{ "title": "In Progress" }`
   Then a new column is appended at the end of the column list and the API returns HTTP 201 with the new column's `id`, `title`, `position`, and `boardId`

2. Given an existing column
   When an Admin/owner calls `PATCH /api/boards/:boardId/columns/:columnId` with `{ "title": "Doing" }`
   Then the column title is updated and the API returns HTTP 200 with the updated column

3. Given an existing column with no cards
   When an Admin/owner calls `DELETE /api/boards/:boardId/columns/:columnId`
   Then the column is deleted and the API returns HTTP 204

4. Given an existing column with one or more cards
   When an Admin/owner calls `DELETE /api/boards/:boardId/columns/:columnId`
   Then the API returns HTTP 409 indicating the column must be empty before deletion

5. Given two or more columns on a board
   When an Admin/owner calls `PATCH /api/boards/:boardId/columns/reorder` with `{ "orderedIds": ["id3", "id1", "id2"] }`
   Then all affected columns have their `position` values updated to reflect the new order and the API returns HTTP 200

6. Given a Member (team board) or non-owner user attempting any column mutation
   When the request is received
   Then the API returns HTTP 403

**Edge Cases:**

- Reorder payload with missing column IDs: If `orderedIds` does not contain every column ID belonging to the board, the API returns HTTP 422.
- Duplicate column title: Allowed — no uniqueness constraint on column titles within a board.

### US-6: Card CRUD and Movement

**As a** team Member or Admin (team board), or the board owner (personal board)
**I want to** create, edit, move, reorder, and delete cards
**So that** I can track individual tasks and update their status

**Acceptance Criteria:**

1. Given an authenticated user with at least Member access to the board
   When they call `POST /api/boards/:boardId/columns/:columnId/cards` with `{ "title": "Write unit tests" }`
   Then a new card is created at the bottom of the column and the API returns HTTP 201 with the card's `id`, `title`, `columnId`, `position`, and `createdAt`

2. Given an existing card
   When a Member/Admin calls `PATCH /api/boards/:boardId/cards/:cardId` with any subset of editable fields (title, description)
   Then only the provided fields are updated and the API returns HTTP 200 with the full updated card

3. Given an existing card
   When a Member/Admin calls `PATCH /api/boards/:boardId/cards/:cardId/move` with `{ "targetColumnId": "...", "position": 2 }`
   Then the card is reassigned to `targetColumnId` and inserted at the specified position, with all other cards in the source and target columns having their positions adjusted accordingly

4. Given cards within a single column
   When a Member/Admin calls `PATCH /api/boards/:boardId/columns/:columnId/cards/reorder` with `{ "orderedIds": [...] }`
   Then card positions within that column are updated to match the provided order

5. Given an existing card
   When a Member/Admin calls `DELETE /api/boards/:boardId/cards/:cardId`
   Then the card and all its child data (comments, checklist items, attachment records) are deleted and the API returns HTTP 204

6. Given a user with no access to the board
   When they attempt any card operation
   Then the API returns HTTP 403

**Edge Cases:**

- Moving a card to a non-existent column: API returns HTTP 404.
- Position out of range: If `position` exceeds the number of cards in the target column, the card is appended at the end without error.
- Reorder payload with missing card IDs: API returns HTTP 422.

### US-7: Card Detail Fields — Due Date and Assignees

**As a** team Member or Admin
**I want to** set a due date and assign team members to a card
**So that** the team knows who is responsible and when the task should be completed

**Acceptance Criteria:**

1. Given an existing card
   When a Member/Admin calls `PATCH /api/boards/:boardId/cards/:cardId` with `{ "dueDate": "2026-06-01T00:00:00Z" }`
   Then the card's `dueDate` field is stored as a UTC datetime and returned in subsequent GET responses

2. Given an existing card with a due date
   When a Member/Admin calls `PATCH /api/boards/:boardId/cards/:cardId` with `{ "dueDate": null }`
   Then the due date is cleared from the card

3. Given an existing card
   When a Member/Admin calls `POST /api/boards/:boardId/cards/:cardId/assignees` with `{ "userId": "..." }`
   Then the specified user is added to the card's `assignees` list; if they are already assigned, the operation is idempotent and returns HTTP 200

4. Given an existing card with an assignee
   When a Member/Admin calls `DELETE /api/boards/:boardId/cards/:cardId/assignees/:userId`
   Then that user is removed from the `assignees` list and the API returns HTTP 204

**Edge Cases:**

- Assigning a user not belonging to the board's team: For team boards, the API returns HTTP 422 if the target user is not a member of the board's team.
- Invalid ISO 8601 date: API returns HTTP 422 with a descriptive validation error.

### US-8: Card Comments

**As a** team Member or Admin
**I want to** add, edit, and delete comments on a card
**So that** I can communicate context and decisions directly on the relevant task

**Acceptance Criteria:**

1. Given an existing card
   When a Member/Admin calls `POST /api/boards/:boardId/cards/:cardId/comments` with `{ "body": "Needs review" }`
   Then a comment is created with the author's `userId`, `body`, and `createdAt`, and the API returns HTTP 201

2. Given an existing comment authored by the requesting user
   When they call `PATCH /api/boards/:boardId/cards/:cardId/comments/:commentId` with `{ "body": "Updated text" }`
   Then the comment body is updated, an `updatedAt` timestamp is set, and the API returns HTTP 200

3. Given an existing comment authored by a different user
   When a non-Admin Member attempts to edit it
   Then the API returns HTTP 403

4. Given an existing comment authored by the requesting user or a team Admin
   When they call `DELETE /api/boards/:boardId/cards/:cardId/comments/:commentId`
   Then the comment is deleted and the API returns HTTP 204

5. Given a card
   When a user calls `GET /api/boards/:boardId/cards/:cardId`
   Then the response includes a `comments` array with each comment's `id`, `body`, `authorId`, `createdAt`, and `updatedAt`

**Edge Cases:**

- Empty comment body: API returns HTTP 422.
- Comment body exceeding 10,000 characters: API returns HTTP 422.

### US-9: Card Checklists

**As a** team Member or Admin
**I want to** add a checklist with items to a card
**So that** I can track subtasks within a single card

**Acceptance Criteria:**

1. Given an existing card
   When a Member/Admin calls `POST /api/boards/:boardId/cards/:cardId/checklists` with `{ "title": "QA Steps" }`
   Then a checklist is created with an empty `items` array and the API returns HTTP 201

2. Given an existing checklist
   When a Member/Admin calls `POST /api/boards/:boardId/cards/:cardId/checklists/:checklistId/items` with `{ "text": "Run linter" }`
   Then a checklist item is appended with `text`, `checked: false`, and a stable `id`, returning HTTP 201

3. Given an existing checklist item
   When a Member/Admin calls `PATCH /api/boards/:boardId/cards/:cardId/checklists/:checklistId/items/:itemId` with `{ "checked": true }`
   Then the item's `checked` state is toggled and the API returns HTTP 200

4. Given an existing checklist item
   When a Member/Admin calls `PATCH` with `{ "text": "Run linter and formatter" }`
   Then the item text is updated and the API returns HTTP 200

5. Given an existing checklist
   When a Member/Admin calls `DELETE /api/boards/:boardId/cards/:cardId/checklists/:checklistId`
   Then the checklist and all its items are deleted and the API returns HTTP 204

**Edge Cases:**

- Empty checklist item text: API returns HTTP 422.
- A card may have more than one checklist (no upper limit enforced at the API level in this requirement; the architect may choose to set one).

### US-10: Card Attachments

**As a** team Member or Admin
**I want to** attach files to a card
**So that** relevant documents or screenshots are accessible directly from the task

**Acceptance Criteria:**

1. Given an existing card
   When a Member/Admin calls `POST /api/boards/:boardId/cards/:cardId/attachments` with a multipart form containing a file
   Then the file is stored (via Railway volumes or object storage, TBD by architect), an attachment record is created with `id`, `filename`, `mimeType`, `sizeBytes`, `url`, `uploadedBy`, and `createdAt`, and the API returns HTTP 201

2. Given a card with attachments
   When a user calls `GET /api/boards/:boardId/cards/:cardId`
   Then the response includes an `attachments` array with each attachment's metadata (no binary content inlined)

3. Given an existing attachment
   When a Member/Admin calls `DELETE /api/boards/:boardId/cards/:cardId/attachments/:attachmentId`
   Then the attachment record is deleted, the stored file is removed from storage, and the API returns HTTP 204

**Edge Cases:**

- File size limit: The maximum accepted file size is to be determined by the architect based on Railway volume or object storage constraints. The API must return HTTP 413 if the limit is exceeded.
- Unsupported MIME type: The allowlist of accepted MIME types is to be determined by the architect. The API must return HTTP 415 for rejected types.
- Storage write failure: If the file cannot be persisted, the attachment record must not be created; the API returns HTTP 500 and logs the error.

### US-11: Label CRUD

**As a** team Admin (team board) or board owner (personal board)
**I want to** create, rename, recolor, and delete labels
**So that** cards can be categorised visually

**Acceptance Criteria:**

1. Given an authenticated Admin/owner
   When they call `POST /api/boards/:boardId/labels` with `{ "name": "Bug", "color": "#e11d48" }`
   Then a label is created scoped to that board and the API returns HTTP 201 with `id`, `name`, `color`, and `boardId`

2. Given an existing label
   When an Admin/owner calls `PATCH /api/boards/:boardId/labels/:labelId` with `{ "color": "#16a34a" }`
   Then only the provided fields are updated and the API returns HTTP 200

3. Given an existing label
   When an Admin/owner calls `DELETE /api/boards/:boardId/labels/:labelId`
   Then the label is deleted, all card-label associations for that label are removed, and the API returns HTTP 204

4. Given an existing card
   When a Member/Admin calls `POST /api/boards/:boardId/cards/:cardId/labels` with `{ "labelId": "..." }`
   Then the label is associated with the card; if already associated, the operation is idempotent and returns HTTP 200

5. Given a card with a label applied
   When a Member/Admin calls `DELETE /api/boards/:boardId/cards/:cardId/labels/:labelId`
   Then the association is removed and the API returns HTTP 204

**Edge Cases:**

- Color must be a valid CSS hex color string (3 or 6 hex digits, prefixed with `#`); otherwise API returns HTTP 422.
- Label name must be non-empty and at most 50 characters; otherwise API returns HTTP 422.
- Labels are scoped per board; a label from board A cannot be applied to a card on board B.

### US-12: Team Member Management

**As a** team Admin
**I want to** view team members and change their roles
**So that** I can control who has elevated permissions on the team board

**Acceptance Criteria:**

1. Given an authenticated team member
   When they call `GET /api/teams/:teamId/members`
   Then the API returns a list of all members with `userId`, `email`, `role`, and `joinedAt`

2. Given an authenticated team Admin
   When they call `PATCH /api/teams/:teamId/members/:userId` with `{ "role": "admin" }`
   Then the target user's role is updated to Admin and the API returns HTTP 200

3. Given an authenticated team Admin
   When they call `PATCH /api/teams/:teamId/members/:userId` with `{ "role": "member" }`
   Then the target user's role is demoted to Member and the API returns HTTP 200

4. Given a team Admin attempting to demote themselves
   When they are the only remaining Admin on the team
   Then the API returns HTTP 409 indicating at least one Admin must remain

5. Given a team Member attempting to change another member's role
   When the request is received
   Then the API returns HTTP 403

**Edge Cases:**

- Target user not in the team: API returns HTTP 404.
- Invalid role value (not "admin" or "member"): API returns HTTP 422.

### US-13: Real-Time Board Updates via SSE

**As a** user viewing a board
**I want to** see changes made by other users reflected immediately on my screen
**So that** I do not need to refresh the page to stay in sync during collaborative editing

**Acceptance Criteria:**

1. Given an authenticated user
   When they call `GET /api/boards/:boardId/events` with an `Accept: text/event-stream` header
   Then the API establishes an SSE connection that remains open and streams events to the client

2. Given an open SSE connection for board B
   When any other user performs a write operation on board B (column created/updated/deleted/reordered, card created/updated/moved/deleted, label change, comment added/updated/deleted, checklist change, attachment added/deleted)
   Then the API emits an event on the SSE stream with `event` type identifying the mutation and `data` containing the affected resource's updated state as JSON

3. Given a user whose session expires while an SSE connection is open
   When the next event would be emitted
   Then the server closes the SSE connection with an appropriate error event before terminating it

4. Given a client that disconnects (e.g., tab closed)
   When the server detects the connection is gone
   Then the server cleans up the subscription without error or resource leak

**Edge Cases:**

- Board not found: `GET /api/boards/:boardId/events` returns HTTP 404 before upgrading to SSE if the board does not exist.
- User not authorised for the board: Returns HTTP 403 before upgrading to SSE.
- High-concurrency fan-out: The architect must determine whether a Pub/Sub mechanism (e.g., MongoDB Change Streams) or in-process event bus is used to broadcast to all SSE subscribers for a given board.

## Technical Considerations

- **Monorepo package**: The API lives at `apps/api` within the existing pnpm monorepo. It must have its own `package.json` and `tsconfig.json`. Shared tooling (ESLint, Prettier, TypeScript base config) may be inherited from the workspace root.
- **Framework**: Hono running on the Node.js adapter (`@hono/node-server`). Hono's built-in `streamSSE` helper is the preferred SSE primitive.
- **Database**: MongoDB accessed via the official Node.js driver or Mongoose (architect's choice). All write operations affecting ordering must be performed as atomic operations or transactions where MongoDB supports them.
- **Auth**: Better Auth (`better-auth`) with the Google OAuth plugin. Domain allow-list enforcement must be implemented as middleware that runs before session creation, inspecting the email domain returned by Google.
- **Environment variables required**: `MONGODB_URI`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `ALLOWED_DOMAINS` (comma-separated list of permitted email domains).
- **Deployment**: Railway. The architect must define the Railway service configuration and ensure environment variables are documented.
- **File attachments storage**: Railway volumes or an external object storage service (e.g., S3-compatible). The specific mechanism is left to the architect. The API contract (US-10) is storage-agnostic.
- **Real-time**: SSE over HTTP/1.1. WebSockets are not required. The architect must decide whether MongoDB Change Streams or an in-process event emitter is used to fan out events to connected SSE clients.
- **Authorization model**: Two board types (personal, team). Personal boards: only the owning user may access. Team boards: all team members may read and write cards/comments; only Admins may mutate columns and team settings.
- **Position management**: Card and column ordering is managed via a `position` integer field. The architect must choose a position-numbering strategy (e.g., sparse integers, fractional indexing) that minimises re-numbering on reorder.
- **Error response format**: All error responses must use a consistent JSON envelope, e.g., `{ "error": { "code": "FORBIDDEN", "message": "..." } }`.

## Out of Scope

- Frontend implementation — no Svelte components, HTML, or CSS.
- Multiple personal boards per user — exactly one personal board per user.
- Multiple team boards per team — exactly one team board per team.
- Invitation-based team membership — domain auto-join is the only onboarding path.
- Gantt or timeline views.
- Card voting, reactions, or emoji responses.
- Email or push notifications.
- Webhooks or third-party integrations.
- Board archiving or soft-delete.
- Audit logging beyond application-level error logs.
- Rate limiting — out of scope for this requirement; the architect may add it as a cross-cutting concern.
