# Dependency Updates and Node 24

## Summary

This is a routine maintenance update to keep the project aligned with the current Node.js LTS release and the latest versions of all npm dependencies. The project is a SvelteKit application using `@sveltejs/adapter-node`, Tailwind CSS v4, and Shadcn Svelte (via `bits-ui`).

The update covers three distinct areas: bumping all npm packages in `package.json` to their latest available versions, upgrading the Dockerfile base image across all three build stages from `node:20-alpine` to `node:24-alpine`, and updating the `.nvmrc` and `package.json` `engines` field to reflect Node 24 as the minimum supported runtime.

The goal is to reduce accumulated dependency drift, pick up security patches and performance improvements in upstream packages, and ensure the local development environment and the production Docker image run on the same Node.js version.

## User Stories

### US-1: Upgrade npm dependencies to latest versions

**As a** developer maintaining the project
**I want to** update all npm packages to their latest released versions
**So that** the project benefits from bug fixes, security patches, and new features without manual version-by-version research

**Acceptance Criteria:**

1. Given the current `package.json` with pinned semver ranges
   When `npm-check-updates` (or equivalent) is run and applied
   Then every dependency in both `dependencies` and `devDependencies` is updated to the latest version available on the npm registry

2. Given updated package versions in `package.json`
   When `npm install` is run
   Then `package-lock.json` is regenerated and reflects the new resolved versions

3. Given the updated `node_modules`
   When `npm run build` is executed
   Then the build completes without errors and produces a valid `build/` output directory

4. Given the updated `node_modules`
   When `npm run check` (svelte-check) is executed
   Then no TypeScript or Svelte type errors are reported

**Edge Cases:**

- Breaking major version bump: If any package introduces a breaking API change detected by the type checker or build, the specific package must be noted and either pinned to the last compatible version or the breaking change must be resolved before the update is considered complete.
- Peer dependency conflicts: If `npm install` reports unresolvable peer dependency warnings that cannot be satisfied simultaneously, the conflicting packages must be identified and the lowest-impact resolution documented.

---

### US-2: Upgrade Docker base image to node:24-alpine

**As a** developer deploying the application via Docker
**I want to** change all three Dockerfile stages from `node:20-alpine` to `node:24-alpine`
**So that** the production container runs on the same Node.js major version as the local development environment

**Acceptance Criteria:**

1. Given the current Dockerfile with three stages (`deps`, `build`, `runtime`) all referencing `node:20-alpine`
   When the Dockerfile is updated
   Then all three `FROM` directives reference `node:24-alpine`

2. Given the updated Dockerfile
   When `docker build` is executed targeting the `runtime` stage
   Then the image builds successfully with no errors

3. Given the built Docker image
   When `node --version` is executed inside the container
   Then the output reports a Node.js 24.x version

4. Given the built Docker image
   When the container is started and the SvelteKit adapter-node server initialises
   Then the application responds to HTTP requests on the configured port (3000)

**Edge Cases:**

- Alpine package availability: If any native dependency or OS package used during the build stage does not exist in the `node:24-alpine` image, an explicit `apk add` step must be added to the relevant stage.

---

### US-3: Update local Node.js version declarations to 24

**As a** developer setting up or switching to this project locally
**I want to** have `.nvmrc` and `package.json` engines reflect Node 24
**So that** `nvm use` automatically selects the correct runtime and CI/CD tooling enforces the right version

**Acceptance Criteria:**

1. Given the current `.nvmrc` containing `20`
   When the file is updated
   Then `.nvmrc` contains exactly `24`

2. Given the current `package.json` `engines.node` field set to `>=20`
   When the file is updated
   Then `engines.node` is set to `>=24`

3. Given the updated `.nvmrc`
   When a developer runs `nvm use` in the project root
   Then nvm selects a Node.js 24.x installation without errors

**Edge Cases:**

- No Node 24 installed locally: If the developer does not have Node 24 installed via nvm, `nvm use` will fail with a version-not-found message. This is expected; the developer must run `nvm install 24` first. No project-level workaround is required.

---

### US-4: Verify end-to-end build integrity after all updates

**As a** developer merging this maintenance change
**I want to** confirm the full build pipeline passes after all updates are applied together
**So that** no combination of dependency and runtime changes causes a regression

**Acceptance Criteria:**

1. Given all changes from US-1, US-2, and US-3 applied simultaneously
   When `npm run build` is executed under Node 24
   Then the build succeeds and the `build/` output directory is present and non-empty

2. Given the successful npm build
   When the Docker image is built from the updated Dockerfile
   Then the image builds without errors in all three stages

3. Given the runtime Docker image
   When the container starts
   Then the SvelteKit adapter-node server starts and the application is reachable

**Edge Cases:**

- Partial failure: If the npm build passes but the Docker build fails (or vice versa), each failure must be treated as a separate blocking issue and resolved before the change is merged.

## Technical Considerations

- The Dockerfile uses a three-stage build (`deps`, `build`, `runtime`). All three `FROM` lines must be updated; missing any one stage will result in an inconsistent image.
- `npm-check-updates` (`ncu -u`) is the recommended tool for bulk version bumping. After running it, `npm install` must be re-run to regenerate `package-lock.json`.
- Tailwind CSS v4 and `@tailwindcss/vite` are tightly coupled. If one is bumped to a new minor or major, the other should be bumped to match to avoid configuration incompatibilities.
- `bits-ui` (Shadcn Svelte's underlying primitive library) and `svelte` / `@sveltejs/kit` may have coordinated release cycles. If a major version of `bits-ui` is available, verify it is compatible with the targeted Svelte version before accepting the update.
- `typescript` is currently at `^6.0.2`. A major bump here may affect `svelte-check` output. Run `npm run check` explicitly after updating TypeScript.
- Node.js 24 ships with an updated V8 and changed default flags. No application-level changes are anticipated, but the build verification step (US-4) is the safety net.
- `package-lock.json` must be committed alongside `package.json` so that `npm ci` in the Docker `deps` stage uses exact resolved versions.

## Out of Scope

- Adding new dependencies or removing existing ones beyond what the version updates require.
- Migrating from one adapter to another (e.g., `adapter-node` to `adapter-auto`).
- Changing CI/CD pipeline definitions beyond what is strictly necessary to reflect the Node 24 version.
- Upgrading from Tailwind CSS v4 to a hypothetical v5 or any other framework-level migration.
- Modifying application source code, Svelte components, or business logic.
- Adding or removing Docker Compose files or other infrastructure files not mentioned in the user's request.
