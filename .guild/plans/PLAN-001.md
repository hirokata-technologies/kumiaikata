# Dependency Updates and Node 24 Implementation Plan

## Architecture Overview

This is a maintenance-only change with no source-code modifications. The work touches four files that together pin the project's runtime and dependency surface:

- `package.json` — bumps every entry in `dependencies` and `devDependencies` to its latest published version and raises `engines.node` from `>=20` to `>=24`.
- `package-lock.json` — regenerated by `npm install` after `package.json` is rewritten.
- `.nvmrc` — single token bumped from `20` to `24`.
- `Dockerfile` — three `FROM node:20-alpine` directives (stages `deps`, `build`, `runtime`) all changed to `node:24-alpine`.

The work splits cleanly along two axes: (a) the JavaScript dependency surface and Node version declarations consumed by local tooling, and (b) the Docker image's base layer. They are sequenced so that the npm side lands first — its `package-lock.json` is the input to the Docker `deps` stage via `npm ci`, so verifying the npm build under Node 24 before rebuilding the image avoids debugging two unknowns at once.

## Codebase Analysis

The project is a single-package SvelteKit application using `@sveltejs/adapter-node`. Relevant facts confirmed by reading the files:

- `package.json` (37 lines): `engines.node` is currently `>=20`. Dependencies include the Svelte 5 / SvelteKit 2 stack, Tailwind v4 (`tailwindcss` + `@tailwindcss/vite`), Shadcn-style primitives via `bits-ui`, plus small utilities (`clsx`, `tailwind-merge`, `tailwind-variants`, `tw-animate-css`, `lucide-svelte`). TypeScript is already at `^6.0.2`.
- `.nvmrc`: contains the single token `20`.
- `Dockerfile` (32 lines): three-stage build (`deps`, `build`, `runtime`), each `FROM node:20-alpine`. Build stage runs `npm run build` then `npm prune --omit=dev`. Runtime copies `build/`, `node_modules/`, and `package.json` only, runs as the `node` user, exposes port 3000, and starts with `node build`.
- `docker-compose.yml` exists at the repo root but is explicitly out of scope per REQ-001.
- `svelte.config.js`, `vite.config.ts`, `tsconfig.json`, `components.json` exist and are configuration files for the existing stack — no changes anticipated, since no version bump in the request implies a config migration. If a major bump surfaces a config-format change at `npm run check` or `npm run build` time, the developer must surface it as a blocker rather than silently edit config.
- `src/`, `static/`, `build/` are application and output directories — untouched by this work.
- No CI workflow files were found at the repo root; CI/CD changes are out of scope anyway.
- `.guild/docs/` is empty — no prior research applies.

Existing conventions to follow:

- `package.json` uses tab indentation. Preserve it.
- `Dockerfile` uses `# syntax=docker/dockerfile:1.7` and tagged multi-stage builds. Only the image tag changes; structure stays.
- `npm ci` (not `npm install`) is used inside Docker — therefore `package-lock.json` must be committed and consistent with `package.json`.

## Technical Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Bulk-bump tool | `npm-check-updates` (`npx ncu -u`) | Explicitly recommended in REQ-001's Technical Considerations; standard idiom for blanket "latest" bumps and avoids hand-editing every range. |
| Node version pin syntax | `>=24` in `engines.node`, bare `24` in `.nvmrc` | Mirrors the existing format (`>=20` and `20`); REQ-001 US-3 specifies these exact values. |
| Task ordering | npm bumps first, then Dockerfile | The Docker `deps` stage runs `npm ci` against the committed `package-lock.json`. Landing npm changes first means the Docker rebuild verifies against a known-good lockfile, isolating Docker-only failures (e.g., missing alpine packages) from npm resolution failures. |
| Breaking-change posture | Stop and report, do not silently downgrade or patch | REQ-001 US-1 edge case requires that any breaking bump be either pinned back or resolved deliberately. Source code changes are out of scope, so the default response to a breaking change is to flag it for human decision rather than rewrite application code. |
| Verification commands | `npm run build` + `npm run check` for npm side; `docker build` + container smoke test (curl localhost:3000) for Docker side | These are exactly the commands named in REQ-001's acceptance criteria for US-1, US-2, and US-4. |
| Lockfile regeneration | Delete-and-rebuild not required; `npm install` after `ncu -u` is sufficient | `npm install` updates the lockfile in place to match the new `package.json` ranges. A full delete is overkill and risks losing useful resolution metadata. If install warns about unresolvable peers, fall back to `rm package-lock.json && npm install`. |

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Major version bump in `svelte`, `@sveltejs/kit`, `bits-ui`, `tailwindcss`, `typescript`, or `vite` introduces a breaking API or config-format change. | `npm run check` or `npm run build` fails; merge blocked. | Run `npm run check` and `npm run build` immediately after `npm install`. If a specific package is the culprit, pin it back to the last compatible version in `package.json` and re-run install. Document the pin in the work log. Do not edit application source — that is out of scope. |
| Tailwind v4 + `@tailwindcss/vite` version skew (one bumps, the other does not, or they bump to incompatible minors). | Build-time Tailwind errors. | Verify both packages end up on matching minor/major versions after `ncu -u`. If they diverge, force-align them by hand-editing `package.json` and re-running `npm install`. |
| Peer dependency conflict surfaces during `npm install` (e.g., `bits-ui` peers vs. `svelte` major). | `npm install` either errors or produces warnings that hide a runtime bug. | Inspect the install output. If unresolvable, identify the conflicting pair, pin the lower-impact one back, and document. |
| `node:24-alpine` is missing an OS package previously available in `node:20-alpine` that some native dependency needs during `npm ci` or `npm run build`. | Docker build fails in `deps` or `build` stage. | Inspect the failing layer's error output, add a targeted `apk add --no-cache <pkg>` to the stage that needs it. Keep changes minimal — one stage, one package. |
| `package-lock.json` not committed, causing `npm ci` in Docker to fail. | Docker build fails with "lockfile out of sync." | Slice 1's acceptance checklist explicitly includes committing the regenerated lockfile. Slice 2 verifies by running `docker build`, which exercises `npm ci`. |
| Node 24 changes a default flag or removes a deprecated API that some dependency still uses. | Runtime errors only visible when the server starts, not at build time. | Slice 2 ends with a container smoke test (start container, hit port 3000). This is the safety net called out in REQ-001 US-4. |
| Developer does not have Node 24 installed locally. | `nvm use` fails before any work can be verified. | Expected per REQ-001 US-3 edge case. Developer runs `nvm install 24` first. Not a project-level concern. |
